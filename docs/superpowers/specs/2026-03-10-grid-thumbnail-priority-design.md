# Grid Thumbnail Priority Design (2026-03-10)

## 1. Background And Goal

Current warmup and thumbnail generation has three visible issues:

- Thumbnail generation decodes full source image then resizes, which is expensive for large files.
- Warmup runs serially, so total completion time grows linearly with image count.
- `preview` warmup (`1600`) competes with grid-first perceived performance.

Validated product goal for this design:

- Priority: grid first-screen responsiveness.
- UX target: within `1s` after entering grid view, at least `90%` of visible items show a thumbnail.
- Warmup scope for first-screen: visible area + one screen ahead/behind.

## 2. Scope

In scope:

- Thumbnail strategy and scheduling for grid/cull rail/preview.
- Cache layer role split (memory vs persistent).
- Concurrency, queue priority, and cancellation.
- Telemetry and acceptance criteria.

Out of scope:

- Replacing image backend library in this phase.
- New persistent thumbnail profile types beyond existing `grid` and `preview`.

## 3. Unified Thumbnail Model

Keep only two persistent categories:

- `grid`: used by grid cards and cull rail.
- `preview`: used by cull/lightbox main image (`1600`).

Do not add a third persistent `fast` profile.

`fast` is defined as an in-memory transient stage for grid rendering only:

- No disk write.
- No new persistent cache key/profile.
- Can be evicted any time.

## 4. Grid Size Buckets

Reduce persistent grid size buckets to two:

- `256`
- `512`

Selection rule:

- Request maps to nearest bucket (`256` or `512`).
- First-screen always prioritizes `256`.
- `512` is background quality upgrade for already visible/nearby items.

## 5. Cache Architecture

### 5.1 Memory Fast Layer (Transient)

- Type: LRU.
- Bound: fixed memory budget (MB), not item count.
- Initial default budget: `96MB`.
- Eviction: oldest first when over budget.
- Occupancy estimate: `w * h * 4` bytes per decoded thumbnail.

This prevents memory growth with large libraries.

### 5.2 Persistent Layer

- Keep existing `profile + size + file metadata` key strategy.
- Persistent writes only for `grid(256|512)` and `preview(1600)`.
- Existing old bucket files remain valid but are not newly generated by new strategy.

## 6. Task Scheduling

Priority queue (highest to lowest):

1. P0: visible range `grid-256`
2. P1: neighbor range (±1 screen) `grid-256`
3. P2: visible range `grid-512`
4. P3: neighbor range (±1 screen) `grid-512`
5. P4: background `preview-1600` warmup

Rules:

- Fixed small worker concurrency (`2` or `3`), configurable.
- In-flight dedupe per `(photo, size)` key.
- On scroll/navigation, low-priority pending tasks can be dropped; P0/P1 can preempt.
- If same image needs near-term `256` then `512`, allow shared decode path where feasible.

## 7. Screen-Specific Behavior

### 7.1 Grid View

- Show `grid-256` ASAP from memory or disk cache.
- Upgrade to `grid-512` asynchronously for visible/nearby cells.
- Never swap to original file in grid.

### 7.2 Cull Rail

- Reuse `grid` strategy (same buckets and scheduling).

### 7.3 Cull/Lightbox Main Preview

- Keep existing `preview-1600 -> original` behavior.
- Main preview does not consume `grid-fast` transient layer.

## 8. Failure And Fallback

- `grid-256` generation fail: show placeholder and continue queue.
- `grid-512` fail: keep existing `256` (no flicker rollback).
- `preview-1600` fail: keep current fallback path to original.
- Add local feature flag to switch back to legacy scheduling if needed.

## 9. Acceptance Criteria

Primary KPI:

- `thumb_grid_visible_90_ms <= 1000` for target datasets/hardware profile.

Secondary KPIs:

- Stable interaction during scroll/selection (no regressions in input latency).
- Fast-layer memory remains under configured cap.
- No persistent cache explosion from extra profile types.

## 10. Telemetry

Required metrics:

- `thumb_grid_visible_90_ms`
- `thumb_queue_wait_ms` (by priority)
- `thumb_task_decode_ms`
- `thumb_task_resize_ms`
- `thumb_task_encode_ms`
- `thumb_task_io_ms`
- `thumb_fast_cache_hit_rate`
- `thumb_disk_cache_hit_rate`

## 11. Rollout Plan

Phase 1:

- Implement queue priority + 2-bucket grid + memory fast LRU.
- Add metrics and baseline collection.

Phase 2:

- Tune worker concurrency, memory cap, and prefetch window with data.

Phase 3 (optional):

- If decode remains dominant, evaluate JPEG path optimization (e.g. scaled decode library) without changing model.
